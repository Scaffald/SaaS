## Execution phases

### Phase A — Scope lock (SC-13, ~2h, @boris)

Deliverable: 1-page scope doc on SC-13. Anchored to MAVA conference demo needs.

Must answer:
- Workers are the primary user. Mobile is the primary experience.
- What's in for v1.8.0: communities, reviews (if lightweight)
- What's out: news, dark mode, public-facing web functionality (kept for
  internal/admin/white-label only)
- Employer/business side: handled manually via web/admin/staffing workflow
- Acceptance: scope doc rendered as Linear ticket body or attached markdown.

Blocks Phase D (scope cut). Does **not** block Phase B or C — they run in parallel.

### Phase B — Code-level pre-audit (~3h, engineering)

Walk each flow in `apps/scaffald/app/**` + `packages/supabase/functions/api/routes/**`.
Look for:

- Dead routes (route exists, handler doesn't / handler returns 404 / unported tRPC→REST)
- Swallowed errors (try/catch that returns silently on failure)
- Missing error states (component shows infinite spinner on API failure)
- Hardcoded test data leaking into production paths
- API contract drift (client expects field X, server returns field Y)
- TODO/FIXME marking real gaps

Output: **draft Linear tickets** filed in `Triage` (no `v1.8.0` label yet), one per
finding, with concrete `file:line` refs and a 1-line fix suggestion. They graduate
to real `v1.8.0` tickets in Phase D — or get closed if Boris's audit or SC-13's
scope rules them out.

Each draft ticket title starts with `[pre-audit]` so Phase D can find them fast.

### Phase C — Flow-level audit (~4h, @boris)

Manual walkthrough auth'd as `mwilson@example.com` (onboarded construction user
from the local seed; password `password123`). One pass per flow:

| Audit ticket | Flow | Code surface |
|---|---|---|
| [SC-19](https://linear.app/scaffald/issue/SC-19) | Apply to job | `app/(public)/jobs/[slug]`, `app/(protected)/jobs`, `api/routes/jobs.ts`, `api/routes/applications.ts` |
| [SC-20](https://linear.app/scaffald/issue/SC-20) | Profile creation | `app/(auth)/auth/*`, `app/(protected)/onboarding`, `api/routes/profiles.ts` |
| [SC-21](https://linear.app/scaffald/issue/SC-21) | Certification | `app/(protected)/profile/certifications`, profile certifications API |
| [SC-18](https://linear.app/scaffald/issue/SC-18) | Create job post (employer-side) | `app/(protected)/jobs/create`, `api/routes/jobs.ts` POST |

For each flow document:
- **What works** — exact happy-path steps that succeed
- **What's broken** — step number + observed behavior + expected behavior
- **Friction** — works but takes too many taps, requires unclear input, etc.
- **Mobile implications** — anything web-only that should be reconsidered for the
  mobile-first MVP

Findings land at
`docs/agents/audits/2026-06-XX-worker-flows/{apply-to-job,profile-creation,certification,create-job-post}.md`
and as comments on the respective Linear audit tickets.

**SC-22** consolidates Phase B + Phase C into a single ranked list with severity
buckets (blocker / polish / nit).

### Phase D — Scope cut (~30 min, joint, after A + B + C)

Walk SC-22's master list. For each finding:

| Finding | If… | Action |
|---|---|---|
| **blocker + in-MVP** (per SC-13) | … | File / promote ticket. Label `v1.8.0`. |
| **polish / nit + in-MVP** | … | File ticket. Label `v1.9.0`. |
| **anything + out-of-MVP** | … | Comment with the SC-13 reference and close (won't-fix-this-release). |

Pre-audit drafts from Phase B graduate here: confirmed → label `v1.8.0`, move
`Triage → Todo`, drop the `[pre-audit]` prefix.

Outcome: v1.8.0 scope locked. Target ~10–15 fix tickets, all blockers, all
MVP-aligned.

### Phase E — Fix wave execution (~1–2 weeks, engineering)

Atomic PRs per ticket (same cadence as v1.6.0 / v1.7.0):

- Branch: `clay/sc-X-...` per issue
- PR title: `fix(<area>): <description> (SC-X)`
- `Closes Scaffald/SC-X` in commit body for auto-close on merge

Sequence by priority: blockers in core paths (auth/profile/apply) first, peripheral
last.

Stay in scope. Anything that surfaces mid-flight that wasn't on the Phase D list
goes to v1.9.0 unless it's actively breaking the fix work.

### Phase F — Cut + ship (~1h)

Per [RELEASE-PROCESS.md](../RELEASE-PROCESS.md):

```bash
pnpm release:app 1.8.0   # bump + commit + tag + push
pnpm ship:ios            # EAS build, auto-submit to TestFlight
# wait for TestFlight build to land
pnpm release:promote 1.8.0   # promotes all v1.8.0 In Github → In TestFlight
```

- **Phase A drift.** If SC-13's scope doc isn't tight, Phase D becomes a debate.
  Mitigation: anchor scope to MAVA demo needs.
- **Audit yields too many tickets.** Phase D cuts ruthlessly to blockers.
  Polish goes to v1.9.0.
- **Boris bandwidth.** Phase C is gated on Boris. If he slips, an augmented
  Phase B (more thorough engineering walk) keeps momentum.
- **v1.7.0 QA regressions.** If TestFlight QA finds v1.7.0 regressions, hotfix
  tickets enter v1.8.0 scope automatically.
